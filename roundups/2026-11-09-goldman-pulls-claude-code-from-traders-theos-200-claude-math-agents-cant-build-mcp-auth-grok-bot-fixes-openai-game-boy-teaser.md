## Claude & Anthropic

### Goldman Sachs takes Claude Code away from traders and bankers

Bloomberg [reports](https://www.fa-mag.com/news/goldman-restricts-traders-and-bankers-from-using-some-ai-tools-89026.html) (via Financial Advisor, November 2) that "For months, Goldman allowed bankers to use Anthropic PBC's Claude Code and Microsoft Corp.'s GitHub for work. Now, the bank is limiting the use of those tools to engineers only, according to internal guidance updated in October and seen by Bloomberg News." The change "irked some of its staff". "Strats", who sit "at the intersection of trading, quantitative research and software engineering", keep access. Bloomberg notes that "As recently as July, Goldman Chief Information Officer Marco Argenti touted the 'vibe coding' by non-technical employees at Goldman, such as traders and bankers." Goldman's statement: "After a period of experimentation where we assess a variety of factors including productivity and risk management, we put them in the hands of those who are best suited to leverage them for the long term." Goldman is also a lead underwriter on Anthropic's IPO. The bank already restricted Claude for its Hong Kong staff earlier this year.

A State of AI [write-up](https://www.thestateofai.com/news/goldman-sachs-claude-code-traders-bankers) of the story was Sunday's top story on [Hacker News](https://news.ycombinator.com/item?id=50415628) (752 points, 402 comments). The first comment noted that "Original source appears to be Bloomberg", with State of AI "being some kind of AI-written site run by a spam company". The write-up adds that traders "had been using the tools to monitor client trading flows, model market moves and positions", and that "Over the next few weeks, Goldman's bankers will be marketing shares in a company whose coding agent most of them are no longer allowed to use."

Most HN commenters took Goldman's side:

- cloudednine, on Argenti's line that engineers "improved" trader-built tools: "As someone who has been on the receiving end of many of these tools, I feel 'improved' is doing some heavy lifting here. Completely overhauled to be operationally viable, perhaps. Thrown into the dark recesses of the backlog, more likely."
- hn_go_brrrrr: "I bet engineering loved traders tossing vibe-coded crap across the wall and demanding it be productionized." Scubabear68 said this is old: "For decades Wall Street traders have been throwing spreadsheets over the wall at developers to be productionized."
- steveBK123 listed what banks worry about: "legal/compliance/reglatory/reputational concerns about application access/entitleements, data privacy, data licensing, granular data entitlements, data access (auditable).. approval chains (auditable), as well as actual financial risk."
- Ericson2314 disagreed: "I have a lot more sympathy for non-technical users writing slop than engineers … If the issue is security, a much more interesting problem for the engineering team to do is design the programming environment for the bankers so they cannot hurt themselves. … I hope the bankers rebel hard against this policy change!"
- baalimago read it as a trust problem for the IPO ("the frontier of LLMs were not trusted at Goldman Sachs"). claysmithr replied: "I feel moreso it doesn't trust the users of the product".

## Agentic Coding & Agent Harnesses

### "LLMs are still SO bad at building tools for agents"

Theo [posted](https://x.com/theo/status/2119575130204717336) (1,294 likes, 95K views): "Every time I try to make Opus set up an MCP authentication path, it makes horrible assumptions and builds something that straight up doesn't work". Theo paraphrased the agent's [plan](https://x.com/theo/status/2119577208033587664): "It's simple! We'll just open your browser and then you sign in". The reply: "What if I'm on a remote machine?" The fallback was "just curl this random script to generate a secret, force users to copy-paste an obscure code on mobile, click a link, and then notify the agent when they're done". Conclusion: "I now understand why everyone's MCP servers are so bad. They all vibe coded them."

Then Theo started a [guide](https://x.com/theo/status/2119606132775997905) for agents: "Working on a general "mcp the right way" guide to give my agents in the future. … WHY WOULD YOU RENDER THE MCP URL AS A CLICKABLE LINK FOR USERS??? Seriously, do not trust ANYTHING your agents say about MCP, connection strategies, and "best practices" for agents. They are CLUELESS."

- [@thesimaximalist](https://x.com/thesimaximalist/status/2119609298225360985) explained the bug: "the client gets the MCP endpoint; the browser gets the authorization URL. "It's a URL, make it clickable" skips the distinction the whole auth flow depends on."
- Marcel [said](https://x.com/marcelmarais/status/2119575380671737889) "the worst is agent written MCP tool descriptions". Blake [said](https://x.com/blakeothy/status/2119577280272036017): "Tools should add raw capability now instead of just telling agents what to do". Nick Dobos [said](https://x.com/NickADobos/status/2119578969595126190) it "Says more about MCP than LLms."
- David Cramer [replied](https://x.com/zeeg/status/2119607072824377647) "maybe you arent being ambitious enough with what you ask".
- [@PrathmeshPatel_](https://x.com/PrathmeshPatel_/status/2119667382398640239) suggested testing tools: the MCPJam CLI, caniuse.dev for client capabilities, and the MCP conformance package.

### Slop control: fold the PR description, ban the review bots

Simon Willison [now hides](https://simonwillison.net/2026/Nov/9/details-summary/) agent-written PR descriptions ([tweet](https://x.com/simonw/status/2119650353142747181), 732 likes). Simon's problem with them: "The problem is that they are too good. An agent-written PR description is accurate and comprehensive. … It's not necessarily slop, but it reads like slop!" The fix: "The opening paragraph of my PRs will be carefully selected to act as a high-level explanation of what's going on—the shortest text a human can read that will help get them up to speed." The agent's text goes into a collapsed `<details><summary>` block labeled with the model and effort, "Claude Opus 5.5 Medium" for example. The promise: "the short opener will represent my human judgement as to what is definitely worth their time." The examples are real datasette and llm PRs, such as [datasette #3052](https://github.com/simonw/datasette/pull/3052). Simon's memory trick for the tag order: say "details-summary" out loud.

- David Wimmer [disagreed](https://x.com/onlydwx/status/2119667414480597452): "I don't read them at all. One model writes, four others review. … 1,754 PRs in under six months, solo. Reading them would simply be impossible."
- Asked who writes the top part, Simon [said](https://x.com/simonw/status/2119660713568534600): "Sometimes me, sometimes I'll copy and paste in a sentence the agent wrote if it really is what I want to convey".

Theo [laid down a rule](https://x.com/theo/status/2119567959052231138) (1,663 likes): "If you set up a bot to "review" every PR on the T3 Code repo with nonstop slop comments, you will be banned." Zed [replied](https://x.com/zeddotdev/status/2119582292662538334) "What if I wrote all the comments myself for the love of the slop game". [@daradoescode](https://x.com/daradoescode/status/2119602223873138804): "I had someone's bot keep arguing w/ mine abt windows behavior that was clearly fucking wrong".

dex is [collecting answers](https://x.com/dexhorthy/status/2119524005044768950) for something with swyx and AI Engineer: "What does slop mean to you? … Why does slop happen? … How can we fight and prevent slop?" Some replies: "[slop is stuff nobody read before shipping. code or copy, same thing](https://x.com/amybuildsAI/status/2119527130237182097)", "[code i can't explain if you asked next week](https://x.com/RohanBhanotAI/status/2119528444916867122)", and from Maddie D. Reese, "[Honestly for me it comes down to intent!](https://x.com/maddiedreese/status/2119552085612257574)", which dex [agreed with](https://x.com/dexhorthy/status/2119552935139106862).

### pstack: formal verification skills for implicit state machines

lauren [suggested a prompt](https://x.com/poteto/status/2119521036660314339) (3,754 likes, 157K views) building on Steve Ruiz's "find all of the implicit state machines in my app": "use /create-formal-verification-skill to model these state machines, one skill per subsystem. and use /statechart to visualize my most important user flows". Both are in [pstack](https://github.com/cursor/plugins/tree/main/pstack). lauren [explained](https://x.com/poteto/status/2119606119559782488) that the first creates a skill like "/verify-notifications" with "a formal spec of your notifications system, stating what properties must hold true, then it will do model checking against various possible states to confirm that it's always true". The real use: "[in grok bot, i used this pattern to fix bugs with our notifications system as it was spamming people on their phones even though they were on the desktop client](https://x.com/poteto/status/2119607908338168214)". It helps most "when the state machine spans the network or ipc/rpc layers (hence "implicit")".

### llama-modchip: 284B DeepSeek on a 64GB CPU

[llama-modchip](https://github.com/synchopate/llama-modchip) ([HN](https://news.ycombinator.com/item?id=50411961), 412 points) is a llama.cpp patch set that claims DeepSeek-V4-Flash 284B in "<59GiB RAM" at 9.1-14.7 tok/s on a "pure 64GB CPU at 256K ctx (0 GPUs)". Its "Lossless" default checkpoint is 56.56 GiB, which works out to under 2 bits per weight for 284B parameters. It also wires Claude Code to the local engine. HN's first question was quantization ("I think it's 2 bit?"). walrus01: "I remain exceedingly skeptical of people who are claiming to run fairly large models in ridiculously tiny sizes." intoXbox: "This is quite an obnoxious Readme.md with AI slop." antirez said that "with 128GB of unified RAM it can run even fast", "coding-agent acceptably fast", linking a [demo](https://x.com/antirez/status/2119392658661749175). embedding-shape answered that the video "seems to show it takes ~4 seconds to process 43 input tokens".
