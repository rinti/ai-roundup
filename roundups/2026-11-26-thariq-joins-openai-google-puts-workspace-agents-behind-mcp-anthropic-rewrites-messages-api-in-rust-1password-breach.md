## Google Puts Workspace Agents Behind MCP

- **The policy.** A [Google Workspace Updates post](https://workspaceupdates.googleblog.com/2026/11/mcp-servers-cli-standardized-usage-tiers-now-available.html) dated November 24 makes the Workspace MCP servers and the official Workspace CLI generally available, and adds a rule: "AI agents or similar access tools must use MCP to access Workspace data, rather than calling Workspace REST APIs directly." Technical enforcement begins on February 1, 2027. There are now two usage tiers (Standard at no cost, Scaled for higher quotas), starting with Gmail, Drive and Calendar, and Scaled-tier usage above the free allowance is billed from April 1, 2027. Google says "Over 99% of active developers currently operate within the Standard tier". A new Workspace AI Tools Addendum also bars "using AI agents to scrape Workspace APIs" and long-term storage of some data derived from them.
- **@KentonVarda's read.** [@KentonVarda](https://x.com/KentonVarda/status/2125672484800246142), reposted by both Peter Steinberger and LLMJunky, called it a "Worrying decision by Google to draw a distinction between agentic and deterministic API use". The argument: agents write code, people run it, and both will use the same code together, so the line cannot hold. "So I think the real effect of this decision is: Google REST APIs are deprecated." Google's MCP servers are also "much narrower" than REST and "offer no backwards-compatibility". The prediction: "If Google creates friction for people using agents, people will just stop using Google. All the Google Workspace apps can easily be slopforked at this point."
- **Steinberger.** Asked whether this affects gog and OpenClaw, [Peter Steinberger](https://x.com/steipete/status/2125654555262431248) replied: "huh, so Google finally built an MCP and is now forbidding clis like gog unless you pay them more? classy". Steinberger also reposted [@JPoehnelt](https://x.com/JPoehnelt/status/2125669508719472844): "Thinking back to why I was fired for making gws cli, it was likely an unstated strategy to block AI competition and find a way to meter usage of Google Workspace APIs."

## Claude & Anthropic

- **The Messages API now runs on Rust.** [Anthropic's engineering post](https://www.anthropic.com/research/migrating-api-to-rust) ([tweet](https://x.com/AnthropicAI/status/2125627317263466739), [ClaudeDevs](https://x.com/ClaudeDevs/status/2125628717263372512)) is the most useful read of the day for anyone running agent teams on real systems. API traffic grew roughly 1,800 times from early 2024 to fall 2026, and the Python service could not keep up. Claude wrote a first version of the core request path in about a week. The hard part came after: "Verification, not generation, had become the bottleneck." The result "uses about 70% less CPU per request and cuts median time to first token by about 20%", with no downtime and no feature freeze.
  - **Tests were not enough.** The team had about 700 integration tests, coupled to the Python implementation. Claude ported them along with the code, and an audit of the ported tests "found more than 100 weakened assertions".
  - **Production as the oracle.** The Rust service shadowed live traffic. Every request where the two versions differed left a record. A script ran every 10 to 30 minutes, grouped the records by which fields differed, and alerted a coordinating Claude agent only for a new kind of record. The coordinator gave each kind to a worker agent and opened a Slack thread where engineers could follow and steer.
  - **Two loops and a gate.** Agents could not read customer requests, only a fingerprint of the difference. In a sandbox with both codebases, each agent guessed the cause, wrote its own request to reproduce it, and edited the Rust until the versions matched. That check took under a second. A fix reached shadowed production traffic only after PR review. One rejected fix shows why: the Rust version was missing the web search tool's description because it did not call an internal service yet. An agent copied the text into files, the prompts matched, and the local verifier passed. An engineer turned it down because Rust would still need to call the service.
  - **History.** In 2024 one engineer settled the question for a while with "We are not rewriting the API in go or rust!" [Lance Martin](https://x.com/RLanceMartin/status/2125627070084796562) summed the method up as "we used the Python API as an oracle, set up verification loops, and had a team of agents fix diffs until Rust matched production's observable behavior".
- **Karpathy's USA as a Civilization map.** [Andrej Karpathy](https://x.com/karpathy/status/2125779541952246039) asked Claude to fill a Civilization-style map with real US data: "Opus 5.5 downloaded and parse a ton of public data and 7 hours and 45K lines of code later... it works :)". It uses 31 data sources reconciled onto one 25 km hex grid, with 19 lenses and a City View for 524 metros. Gold yield is GDP, and a city's districts are its real industry specializations. It was built in the Claude Code desktop app with Opus 5.5 on medium and ultracode turned on. One confession: "Claude decided to skip a few states and territories sry". It is live at [karpathy.ai/usaciv](https://karpathy.ai/usaciv/).

## Agentic Coding & Agent Harnesses

- **Rex resumes programs across restarts.** [Mitchell Hashimoto](https://x.com/mitchellh/status/2125713695233970521): "Rex can now resume your programs through a server restart!" It rests on a new terminal protocol, OSC 7577, built with @herdrdev and reviewed by other terminal authors. In the words of the [spec](https://www.superlogical.com/rex/docs/build/program-resume), "the program that knows how to resume itself tells the terminal the command to run, and the terminal can choose to run it on restart". Rex ships with Claude Code support through a session start hook. Hashimoto is direct about the risk: "Program restart in terminals is fundamentally unsafe, so a lot of effort was put into making this as safe as possible." [Armin Ronacher](https://x.com/mitsuhiko/status/2125732652858917125): "Good idea! Before I could even mention it internally @petrroll already added it!"
- **OpenCode extracts its codemode runtime.** [OpenCode](https://x.com/opencode/status/2125702030832349374) published [psychoscript](https://psychoscript.com): "it's a simple package (no wasm) that can directly execute js and pause/resume it mid execution". The site describes a small bytecode VM for a subset of JavaScript that embeds in Node or Bun and can save a paused run to bytes. [Dax](https://x.com/thdxr/status/2125706702544613419) explained why that matters for durable workflows. The simple design saves every function result and replays; instead, "psychoscript has a bytecode vm so it can just snapshot its in memory state and resume without having to replay everything". [James Long](https://x.com/jlongster/status/2125705548020543902) rewrote it from an interpreter to a bytecode VM with OpenCode's Carbon model: "I was able to do this in the background in a day while doing other work". [Dax](https://x.com/thdxr/status/2125703538995274106) also said OpenCode desktop "is becoming fully native" and that this keeps JS plugins possible without a full JS runtime.
- **More from Dax.** On inference: "[OpenCode Go forced us to become good at inference. 350,000 subscribers who's dollars we have to stretch every month](https://x.com/thdxr/status/2125485294355120445)". On the company: "[i told the team a few months ago that we are pivoting from being a company that makes an agent](https://x.com/thdxr/status/2125493170322448545)" … "to being a company that is best in the world at using agents". OpenCode also gained a [video generation tool](https://x.com/opencode/status/2125737965871681587) for connected providers that have video models.
- **Matt Pocock signs off until January.** [Matt Pocock](https://x.com/mattpocockuk/status/2125619044640592189): "New baby on the way, so blocking X for a while." Before leaving, Matt shared [cookout](https://x.com/mattpocockuk/status/2125540436483711074) ("2,000 commits later, still cooking:"), which the [README](https://github.com/mattpocock/cookout) describes as "A self-hosted, Slack-style board where people and agents share channels and threads." Matt says it is not ready, but shows current thinking on code structure. Matt also left [an open question](https://x.com/mattpocockuk/status/2125567797656977783) for people who never compact long-running agents: "How do you know when an agent is overloaded?" And [a warning](https://x.com/mattpocockuk/status/2125561070404428270) about CI: "Automated checks are great but it's so easy to sloptimize them and slow down the whole factory".
- **100 PRs a week at a fintech.** Lauren ([@poteto](https://x.com/poteto/status/2125657724126138682)) recommended [Will Larson's write-up](https://lethain.com/passing-100-prs-in-a-week/): "it really comes down to periodically resurfacing and thinking about the bottlenecks or limiting step in your coding workflow where human review is still required". ## Math & Research

- **Aaronson's post tops Hacker News.** Scott Aaronson's [new post](https://scottaaronson.blog/?p=10379) ([HN](https://news.ycombinator.com/item?id=50646108), 1,300+ points) describes a dinner party spent watching OpenAI and Anthropic upload papers. After the two proofs of VP ≠ VNP and OpenAI's ω = 9/4 came an OpenAI paper with matching upper and lower bounds for the Fourier transform. "I now feel in my bones, for the first time ever, that a proof of P ≠ NP is not far." Aaronson's stance on trust has changed too: "my working assumption by this point is that any proof that comes directly from OpenAI or Anthropic is correct barring information to the contrary". [Simon Willison quoted the post](https://simonwillison.net/2026/Nov/25/scott-aaronson/) on the blog. AINews plotted 64 selected AI-assisted research advances so far this year: "November accounts for 20".
- **Google's Cogentic drops six papers.** A [directory in google-research](https://github.com/google-research/google-research/tree/master/cogentic_research_papers) ([HN](https://news.ycombinator.com/item?id=50642086)) gained six papers dated November 25, among them "Unconditional Integer Factorization in Time L_N[1/3, O(1)]", "Discrete Logarithms in Finite Fields of Fixed Characteristic in Sub-Quasi-Polynomial Time" and "Breaking the Square-Root Barrier for the Log-Rank Conjecture". AINews, citing @AndrewCurran_, says they came from an agent harness on unnamed Gemini 4 models with no announcement. On practical impact, HN's dzaima worked out the constant in the factoring bound and concluded: "So still a bit to go."
- **The factoring rumor.** A second [HN thread](https://news.ycombinator.com/item?id=50643065) ran on rumors that a lab can factor in polynomial time. Aaronson's own wording is careful: "yes, I'm virtually certain, from multiple reliable sources, that the AI labs are now sitting on one or more bombshells in that area", but "I do not wish to be responsible for spreading unverified rumors." HN's pona-a: "Please, have an evidentiary standard." tptacek, on the worst case: "I really don't think any crisis would occur."
- **GRH in Lean, 99% shorter.** [lsernau/grh-lean](https://github.com/lsernau/grh-lean) ([HN](https://news.ycombinator.com/item?id=50648050)) is a shorter Lean 4 proof of RH and GRH for Dirichlet L-functions, produced by an Anthropic employee with colleagues and Claude, based on Levent Alpöge's proof. It comes in a readable edition of about 300,000 lines and a compact one of about 76,000. HN's bananaflag: "From ~17M lines to just ~76k lines, a 99.56% reduction." gregdeon noted the compact one is heavily golfed: "A more sane version is around 300k lines." The README is plain about status: "No mathematician has read it through, and no paper comes with it."
- **One more from OpenAI.** A preprint titled [The polynomial Hirsch conjecture is false](https://github.com/openai/math/blob/main/preprints/Superpolynomial-graph-diameter-of-simple-polytopes-November-24-2026/paper.pdf) also reached the HN front page.

## Security

- **1Password.** [1Password disclosed](https://1password.com/blog/update-on-nov-2026-security-incident) ([tweet](https://x.com/1Password/status/2125642686443258030), [HN](https://news.ycombinator.com/item?id=50644817), 1,300+ points) that an attacker got into an employee's corporate GitHub account and used it "to access source code and push malicious code to backend services, which downloaded administrative data pertaining to our customers". The investigation began on November 19. Taken for a subset of users: names, sign-in emails, account identifiers, creation and last sign-in times, SRP parameters, and tokens from some invitation and recovery emails. The attacker also copied private source code and reached the CI/CD system. Vault contents and keys were not affected. 1Password rotated credentials and lengthened emailed codes from six digits to ten characters.
- **Reactions.** Peter Steinberger reposted [@theonejvo](https://x.com/theonejvo/status/2125653732612612408): "One GitHub account, and attacker code ends up running in backend services that touch customer data. Where was the branch protection? The second reviewer? The deploy gate?" The post warns that the stolen metadata is ideal for phishing. On HN, tptacek: "This is the single most important attack vector for SAAS companies."
